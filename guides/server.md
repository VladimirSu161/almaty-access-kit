# Свой VPS в Serverspace и закрытый прокси

Этот раздел используется после принятия клиентской платформы или в отдельно заказанном испытательном запуске. Кандидат комплекта не является причиной оплачивать неподтверждённую установку.

## 1. Войти и выбрать параметры

Открой [Serverspace](https://serverspace.kz/) → «Регистрация»/«Вход» → свой проект → создание облачного сервера. Прямой [кабинет](https://my.serverspace.kz/). Интерфейс может менять названия вкладок; агент сверяет выбранные параметры по смыслу перед заказом.

Выбери **Алматы**, Ubuntu **24.04 LTS x64**, 1 vCPU, 1 ГБ RAM, 25 ГБ SSD и публичный IPv4. В исходном проекте сначала выбрали Standard, но при создании не оказалось адресов; рабочим стал High Performance. Это история, не правило покупать сразу два сервера. Если нужная площадка недоступна, остановись и обсуди один конкретный доступный вариант у того же провайдера.

Проверь канал и окончательную цену: базовые CPU/RAM могут стоить одинаково, а цена сети отличаться. Опорная историческая сумма — **3 398,45 ₸/месяц от 1 ноября 2026**, не текущая оферта. [Калькулятор](https://serverspace.kz/conditions/price/). Сервис описывает начисления каждые 10 минут; актуальную модель и расходы остановленного сервера нужно сверить перед оплатой. [Официальная страница VPS](https://serverspace.kz/services/vps-server/linux/).

На странице провайдера на дату проверки указаны Visa/Mastercard, выпущенные вне РФ, и минимальное пополнение 1 500 ₸. Доступность конкретной карты проверяет сам владелец. Выпуск карты, KYC и чужие платёжные данные комплект не предоставляет. Сначала подтвердить итоговую цену и срок, затем оплачивать.

## 2. Подготовить административный ключ

Codex создаёт **новый отдельный** ключ SSH, проверив, что выбранное имя ещё свободно. Закрытый ключ остаётся на твоём компьютере с доступом только владельцу. В кабинет загружается только публичная часть `.pub`. Не заменять обычный личный `id_ed25519` и не отправлять приватный файл в чат.

Административный ключ нужен для настройки VPS. Второй отдельный ключ будет только для фонового туннеля, без доступа к shell. У ключа туннеля права будут уже, чем у администратора.

Перед созданием ещё раз проверь ОС, память, диск, сеть, цену и прикреплённый публичный ключ: после пополнения форма может сбросить значения. Подтверди ровно один заказ. Если подготовка зависла — проверь статус/поддержку; не нажимай создание второго экземпляра автоматически.

## 3. Установить доверие к серверу

Дождись готовности и IPv4. Через веб-консоль своего VPS получи fingerprint его SSH host key; сравни с ключом первого подключения. Сам `ssh-keyscan` через ту же неизвестную сеть не является независимым подтверждением. Несовпадение означает остановку и выяснение причины, не `StrictHostKeyChecking=no`.

Убедись по безопасным командам, что это выбранная Ubuntu и нужные ресурсы. Сохранить в журнале версию ОС, CPU/RAM/диск, время проверки; пароли не сохранять. Тариф, пароль и ключ не являются одним и тем же идентификатором.

## 4. Подготовить ОС

Применить обновления безопасности, установить Docker по [официальной инструкции Ubuntu](https://docs.docker.com/engine/install/ubuntu/). Не выполнять неизвестный `curl|sh` из пересказа. Прочитать устанавливающий скрипт/пакеты и проверить источник. Установка происходит на VPS, не на компьютере клиента.

После проверки входа отдельным ключом можно настроить SSH без паролей и сетевые ограничения. Сначала `sshd -t`, затем проверка второй SSH-сессии, затем reload. Не закрывать единственную работающую сессию, пока новый путь не проверен. Не делать глобальный firewall flush. Разрешённый вход SSH сохранить; прокси публикуется только на loopback независимо от firewall.

## 5. Развернуть gost

Полный рецепт и файлы — [server/README.md](../server/README.md). Базовая версия **ginuerzh/gost:2.11.5**, синтаксис v2. Не подставлять `latest` и не смешивать флаги GOST v3.

Сгенерировать длинный случайный пароль локально в файл с правами 600, не печатая его в чат или shell history. Формат файла: одна строка `client ПАРОЛЬ`. На сервере `/etc/almaty-access/proxy.auth`; каталог 700. Передать по уже проверенному SSH, назначить root ownership. В контейнере секрет монтируется read-only как `/run/secrets/proxy.auth`.

Контейнер: порт **127.0.0.1:48921**, restart `unless-stopped`, журналы **max-size=10m, max-file=3**. Доступ к HTTP CONNECT требует пароль; TLS к целевому сервису не расшифровывается. Публичный `0.0.0.0:48921` не допускается. Docker published ports могут обходить простые правила UFW, поэтому одного слова «firewall включён» недостаточно.

Проверить `docker ps` выбранными полями и `ss -lnt`: прокси только на loopback; без пароля запрос получает 407. Не выводить полный inspect/env контейнера. Сохранить image ID/digest и выбранную версию в журнале.

## 6. Создать ограниченный туннель

См. SSH-шаблоны в `server/`. Пользователь `almaty-tunnel`, заблокированный пароль, shell `nologin`, `MaxSessions 0`, `AllowTcpForwarding local`, `PermitOpen 127.0.0.1:48921`. Для ключа — `restrict,port-forwarding,permitopen="127.0.0.1:48921"`. Проверить фактическую конфигурацию через `sshd -T -C ...`, поскольку порядок Include/Match имеет значение.

На клиенте настроить ровно свой ключ и known_hosts. `BatchMode`, `IdentitiesOnly`, `StrictHostKeyChecking`, `ExitOnForwardFailure`; keepalive 15 секунд × 2, ограниченное восстановление службой ОС. Назначение — только локальный порт прокси на VPS.

## 7. Проверить и перейти к своей ОС

В macOS туннель слушает локальный 127.0.0.1:48921; не открывать его домашней сети. В Linux/WSL SSH создаёт файловый `proxy.sock`, а TCP/48921 появится только внутри изолированного сеанса через relay. Отсутствие внешнего TCP listener там ожидаемо. Сначала проверить транспорт по README платформы. Через готовый прокси без API-ключа проверяется `https://api.anthropic.com/v1/models`: 401 означает достижимость API, не оплаченный аккаунт. Через `https://api.ipify.org` сверяется IPv4 со своим VPS. Авторизация прокси передаётся `curl` через stdin/config с закрытыми правами, не строкой процесса.

Сейчас доказан только транспорт. Следующий этап — внешнее ограничение CLI/браузера по README своей платформы, затем [приёмка](verification.md). Если IPv4 не совпал, не входить и не менять сервер на случайный «быстрый».

Для удаления: пользователь подтверждает конкретный сервер и связанные оплачиваемые ресурсы. Сначала прекращаются рабочие сеансы и клиентский автозапуск, затем ресурсы удаляются в кабинете; проверяется отсутствие дальнейшего начисления. Не считать отправленную заявку в поддержку подтверждением удаления.
