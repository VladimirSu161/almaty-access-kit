# Свой сервер в Алматы — 1.0.0

Это рецепт для **нового собственного VPS Ubuntu 24.04 LTS x64**. В этой выдаче нет оплаченного сервера, рабочего IP, ключей или пароля. Команды ниже выполняет Codex получателя после описи и согласования конкретных изменений. Сборка комплекта не запускала их на сервере автора.

## Что получится

`CLI/браузер → локальная защита → SSH → 127.0.0.1:48921 VPS → gost → интернет`.

SSH шифрует путь до VPS. HTTP proxy gost выбирает внешний адрес VPS и требует отдельный пароль. Gost слушает только loopback: открыть его из интернета по адресу сервера нельзя. У SSH-пользователя туннеля нет терминала, SFTP, других назначений forwarding или прав администратора.

## 1. Выбор сервера и исходная опись

1. Человек сам открывает [Serverspace](https://serverspace.kz/), регистрируется и выбирает **Алматы**, Ubuntu 24.04 LTS x64. Перед оплатой проверить именно площадку, итоговую месячную сумму, диск, IPv4 и резервное копирование. Исторический пример цены не является текущим тарифом.
2. Для первого стенда достаточно начать с 1 vCPU, 1 ГБ RAM, диска 25 ГБ; после установки проверить свободную память и диск. Это отправная конфигурация, не обещание производительности для нескольких пользователей.
3. Записать в личный технический журнал IP, ОС и способ входа через консоль провайдера. В общий архив поддержки IP можно скрыть. Пароль кабинета, root-пароль и приватный ключ не записывать в чат.
4. Подготовить отдельный административный ключ на компьютере владельца. `ssh-keygen -t ed25519` запускается с новым явно выбранным именем и интерактивной парольной фразой. Существующий ключ не перезаписывать. Открытый `.pub` установить через штатный интерфейс провайдера. Приватный ключ остаётся локально.
5. Через консоль провайдера получить `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`. Сверить fingerprint с первым SSH-подключением. `ssh-keyscan` только получает ключ, не удостоверяет сервер. Не применять `StrictHostKeyChecking=no`, не удалять старую запись при неожиданном изменении ключа.

Сначала только прочитать:

```sh
cat /etc/os-release
uname -m
df -h /
free -h
sudo ss -lntup
sudo sshd -t
sudo systemctl status ssh --no-pager
```

Если сервер уже обслуживает чужие задачи, остановиться на описи и адаптировать план. Не менять глобальные правила firewall. Во внешнем firewall провайдера нужен SSH TCP/22 с согласованных адресов; TCP/48921 открывать не нужно. Не включать новый UFW вслепую: это может оборвать администрирование.

## 2. Создание своих секретов

На компьютере получателя выбрать новый каталог `~/.config/almaty-access`, права 700. Если он существует, прочитать его опись и продолжить существующую настройку. Не генерировать ключи повторно поверх файлов. Для автотуннеля создать **другой** ключ:

```sh
ssh-keygen -t ed25519 -f "$HOME/.config/almaty-access/tunnel_ed25519" -C almaty-access-tunnel
```

Команда спрашивает парольную фразу интерактивно. Автозапуск с `BatchMode=yes` не сможет спрашивать её. Для автономного ограниченного ключа допускается сознательно выбрать пустую фразу; тогда важны права 600, шифрование диска и ограничение ключа на сервере. Ключ администратора остаётся отдельным и защищённым. Подключение ssh-agent — отдельная испытанная конфигурация, не скрытый шаг.

Сгенерировать `proxy.auth` только локально, не показывая содержимое (Python 3):

```python
from pathlib import Path
import os, secrets
p = Path.home() / ".config/almaty-access/proxy.auth"
fd = os.open(p, os.O_WRONLY | os.O_CREAT | os.O_EXCL, 0o600)
with os.fdopen(fd, "w") as f:
    f.write("client " + secrets.token_hex(32) + "\n")
print("Создан новый proxy.auth; значение не показано.")
```

`O_EXCL` прекращает работу, если файл уже существует. Формат ровно `client`, пробел, 64 символа hex, перевод строки. Не использовать пароль в `curl -U`, URL командной строки, shell history, Compose environment или `docker run -L user:password@...`. CLI читает его из файла в окружение процесса: окружение тоже секретно, его не снимать в отчёт (`ps e`, `env`, debug dumps запрещены).

## 3. Docker и закрытый proxy

На новом Ubuntu согласовать установку пакетов. Сначала посмотреть симуляцию:

```sh
sudo apt-get update
sudo apt-get -s install docker.io docker-compose-v2
```

После согласованной описи пакетов:

```sh
sudo apt-get install docker.io docker-compose-v2
sudo systemctl enable --now docker
sudo install -d -m 700 /etc/almaty-access
```

Версии `docker --version` и `docker compose version` записать. Если используешь официальный Docker repository, следуй [инструкции Docker для Ubuntu](https://docs.docker.com/engine/install/ubuntu/), не смешивай две установки. Не выполнять случайный `curl | sh` и не добавлять обычного клиента в группу `docker` — доступ к Docker равен административным правам.

Через **административный** SSH передать только свой `proxy.auth` и подготовленный `compose.yaml` в временный приватный каталог сервера. `scp -i <путь-к-админ-ключу> <файл> <админ>@<свой-IP>:<временный-путь>` передаёт пути, не значения секретов. Команда здесь схема: Codex подставляет проверенные пути как отдельные аргументы. Затем `sudo install -m 600 <временный-proxy.auth> /etc/almaty-access/proxy.auth`; удалить именно временный файл после сверки. Сам секрет в терминале не читать.

Перед стартом локально на сервере проверить формат, владельца и права без вывода значения:

```sh
sudo python3 - <<'PY'
import os, re, stat
p = '/etc/almaty-access/proxy.auth'
s = os.lstat(p)
assert stat.S_ISREG(s.st_mode) and s.st_uid == 0
assert stat.S_IMODE(s.st_mode) == 0o600
with open(p, 'rb') as f:
    assert re.fullmatch(rb'client [0-9a-f]{64}\n', f.read())
print('proxy.auth: формат и права верны; значение скрыто')
PY
```

Установить `compose.yaml.template` как `/etc/almaty-access/compose.yaml`, права 600. Шаблон не содержит пароля. На VPS:

```sh
sudo docker compose -f /etc/almaty-access/compose.yaml config --quiet
sudo docker compose -f /etc/almaty-access/compose.yaml pull
sudo docker compose -f /etc/almaty-access/compose.yaml up -d
sudo docker inspect --format '{{.Image}}' almaty-access-proxy
sudo ss -lntp 'sport = :48921'
```

Ожидается **только `127.0.0.1:48921`**, не `0.0.0.0` и не `[::]`. Зафиксировать digest полученного образа. Tag `2.11.5` фиксирует версию; для повторяемого выпуска образ дополнительно закрепляется проверенным digest. Не выдумывать digest до скачивания. `run-gost.sh.template` — равнозначная альтернатива Compose после той же проверки файла; не выполнять оба способа.

`network_mode: host` означает общую сетевую среду с VPS; это **не изоляция клиента**. За закрытый вход отвечает адрес `127.0.0.1` в `-L`. Публикация `ports:`/`-p` здесь не нужна. `unless-stopped` восстанавливает контейнер после сбоя, но не отменяет намеренный `stop`. Журналы ограничены тремя файлами по 10 МБ для этого контейнера; глобальный Docker daemon не меняется. Синтаксис `secrets=` относится именно к [GOST v2](https://v2.gost.run/en/configuration/), не к v3.

До любого входа проверить без пароля:

```sh
curl --max-time 10 --noproxy '' --proxy http://127.0.0.1:48921 https://example.com/ -o /dev/null
```

Ожидается отказ proxy `407`, не успешный ответ сайта. Если без пароля вышел `200`, немедленно остановить только этот контейнер и исправить auth. С компьютера вне VPS проверить, что прямой TCP/48921 недоступен. Успешный внешний тест SSH ничего не говорит о закрытости proxy.

## 4. Ограниченный SSH-пользователь

Держать существующее административное подключение открытым до конца проверки; консоль провайдера должна работать. Создание выполняется только если `getent passwd almaty-tunnel` не нашёл пользователя. Если имя занято — проверить назначение, не менять его вслепую.

```sh
sudo useradd --create-home --shell /usr/sbin/nologin almaty-tunnel
sudo passwd -l almaty-tunnel
sudo chown root:root /home/almaty-tunnel
sudo chmod 755 /home/almaty-tunnel
sudo install -d -o root -g root -m 755 /home/almaty-tunnel/.ssh
```

Из содержимого `authorized_keys.options`, одного пробела и **своего** `tunnel_ed25519.pub` собрать одну строку `/home/almaty-tunnel/.ssh/authorized_keys`. В файле нет приватного ключа. Установить root:root, права 644; каталог выше не должен давать туннельному пользователю заменять ограничения. В `authorized_keys.options` намеренно нет фиктивного публичного ключа: неполная строка не должна случайно пройти за настроенный доступ.

Установить `sshd-almaty.conf.template` как `/etc/ssh/sshd_config.d/60-almaty-access.conf`, root:root 644. Проверить, что основной `sshd_config` включает `sshd_config.d/*.conf`; при иной схеме не дописывать вслепую. OpenSSH использует эффективную совокупность конфигов; другие `Match`/`AllowUsers` могут повлиять на результат.

```sh
sudo sshd -t
sudo sshd -T -C user=almaty-tunnel,host=localhost,addr=127.0.0.1
```

В выводе ожидаются: `authenticationmethods publickey`, `passwordauthentication no`, `kbdinteractiveauthentication no`, `allowtcpforwarding local`, `permitopen 127.0.0.1:48921`, `permitlisten none`, `allowstreamlocalforwarding no`, `allowagentforwarding no`, `permittty no`, `maxsessions 0`, `forcecommand /usr/sbin/nologin`. `DisableForwarding yes` из другого файла заблокирует также нужный туннель — не снимать его без разбора политики.

Только после успешного `sshd -t`: `sudo systemctl reload ssh`. Не `restart`, не отключение старого администратора. Из второго терминала проверить новый административный вход, затем туннельный ключ. [OpenSSH](https://man.openbsd.org/sshd_config) допускает forwarding при `MaxSessions 0`, закрывая shell/SFTP.

## 5. Привязка host key и проверки ограничений

Сверенный публичный host key сохранить локально в `~/.config/almaty-access/known_hosts` (600). `ssh-keyscan -t ed25519 <свой-IP>` можно сохранить во временный файл, проверить `ssh-keygen -lf <файл>` против консоли провайдера и только потом перенести. Адрес в known_hosts должен совпадать с адресом шаблона.

Дальше использовать [macOS](../platforms/macos/README.md) или [Ubuntu](../platforms/linux/README.md), а на Windows сначала [WSL](../platforms/windows/README.md). Linux использует локальный **Unix-сокет → удалённый TCP**: сервер видит TCP forwarding, поэтому `AllowStreamLocalForwarding no` не препятствует этой схеме.

Проверить отдельным новым SSH-процессом: shell и SFTP запрещены; `-R` запрещён; локальный forward к `127.0.0.1:22` и внешнему хосту запрещён **при попытке использования**. Одного `ExitOnForwardFailure=yes` недостаточно: локальный listener может создаться раньше отказа удалённому назначению. Разрешён только TCP `127.0.0.1:48921` на сервере. Не путать `localhost` и `127.0.0.1` в `PermitOpen`.

Для authenticated HTTPS теста диагностический скрипт читает `proxy.auth` сам; не включать пароль в argv. Проверить ожидаемый IP VPS и отдельно отказ с неправильным паролем. HTTP 401 от API без токена — доступность API, не состояние аккаунта.

## Сбой, обновление и адресный откат

- Нет SSH: сверить host key, доступ через консоль, restricted user и ключ. Новый IP после пересоздания VPS — новая проверка, не автоматическое доверие.
- Есть SSH, нет proxy: `sudo docker ps --filter name=almaty-access-proxy`; затем короткий `docker logs --tail 30` локально. Не отправлять сырые журналы с адресами/заголовками в поддержку.
- Для согласованного теста обрыва: `sudo docker stop almaty-access-proxy`; после отрицательных проверок `sudo docker start almaty-access-proxy`. Рабочий сервер другого человека для теста не останавливать.
- Обновление: сохранить текущий image ID/digest и конфиг в Git без секрета; сначала проверить новый образ на стенде. Не переходить с v2 на v3 простой заменой tag. После обновления повторить auth, listen, запрет forward и обрыв.
- Откат SSH-правил: убрать **только** `60-almaty-access.conf`, если он создан этим комплектом; `sshd -t`, затем `reload ssh`. Сначала отключить локальный автотуннель. Не удалять другие ключи, пользователей или firewall rules.
- Отключение proxy: `docker compose -f /etc/almaty-access/compose.yaml stop`; это обратимо. Удаление именно контейнера через `down` и удаление именно своих секретов выполняются отдельным согласованным действием. Никаких `docker system prune`, `ufw reset` или `nft flush ruleset`.
- Удаление VPS останавливает начисления только по правилам провайдера и уничтожает серверные данные; выполняет сам владелец после проверки, что нужных данных там нет.

## Что ещё не подтверждено этим архивом

Шаблоны синтаксически проверяются при сборке; новая чистая установка сервера и реальный маршрут получателя требуют собственного прогона. Не считать генерацию файлов, статус `running` или порт `LISTEN` доказательством безопасной готовности.
