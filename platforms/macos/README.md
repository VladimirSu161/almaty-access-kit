# macOS — шаблоны и порядок проверки

Версия `1.0.0`. Настройка на компьютере получателя до работающего Claude в
отдельном Google Chrome и Claude Code в iTerm2. Архитектура CLI повторяет
изученный sandbox-exec. Chrome использует обязательный proxy и проверку отказа
веб-запросов, без заявления внешнего firewall всех процессов браузера. Новую
машину проверяет агент; авторский рабочий Mac/VPS не трогать.

## Файлы и граница ответственности

| Файл | После подготовки | Что делает |
|---|---|---|
| `proxy-only.sb.template` | `~/.config/almaty-access/proxy-only.sb` | Ограничивает IP-сокеты CLI и его потомков локальным TCP/48921 |
| `claude-almaty.template` | `~/.local/bin/claude-almaty` | Читает proxy.auth, включает proxy-переменные, запускает foreground CLI под профилем |
| `local.almaty-access.tunnel.plist.template` | `~/Library/LaunchAgents/local.almaty-access.tunnel.plist` | Отдельный SSH-процесс с доступом к VPS, восстановление туннеля |
| `chrome-almaty.command.template` | `~/.local/bin/chrome-almaty.command` | Один отдельный профиль: проверка IP по умолчанию, Claude по --claude |

`kit.py prepare` создаёт подготовительную папку, `deployment.json` и отдельные структурированные конфиги. Он **ничего не устанавливает**. Codex читает параметры из `deployment.json`, адаптирует нужные `.template` и проверяет полученные файлы. Нельзя сделать слепой `sed` по всем файлам: пути в shell, XML и systemd экранируются по-разному. Маркеры: `@SERVER_IP@`, `@HOME@`, `@CONFIG_DIR@`, `@CLI_BINARY@`, `@SSH_KEY@`. В shell лучше записывать значение через `shlex.quote`; в plist — `plistlib`. Пробелы и кириллица в путях допустимы после проверки; неиспользованные маркеры — ошибка.

## 1. Опись без изменений

Прочитать общий [SETUP](../../SETUP.md) и пройти очистку прежнего входа только по его отдельному согласованному плану. Рабочие `projects`, `skills`, `hooks`, MCP, память и весь обычный Chrome не сбрасывать.

```sh
sw_vers
uname -m
command -v claude
test -x /usr/bin/sandbox-exec
test -x '/Applications/Google Chrome.app/Contents/MacOS/Google Chrome'
lsof -nP -iTCP:48921 -sTCP:LISTEN
launchctl print "gui/$(id -u)/local.almaty-access.tunnel"
```

Последние две команды при новой установке могут сообщить «не найдено» — это нормальное отсутствие, не неисправность. Если порт занят или служба уже есть, выяснить владельца, исполняемый файл и аргументы процесса; не завершать чужой PID. До изменения нужны версия macOS, архитектура, CLI, Chrome, наличие Python 3.10+, достаточное место. Новые версии macOS могут иначе исполнять `sandbox-exec`: при ошибке разберись по актуальной документации и адаптируй совместимый механизм с теми же проверками. До исправления не запускай обычный Claude как обход.

Если CLI отсутствует, установить его штатным способом из [официальной инструкции](https://code.claude.com/docs/en/setup), отдельно согласовав загрузку и прочитав установщик. Не входить в аккаунт во время установки. Сохранить реальный путь бинарника, а не рекурсивно ссылаться на будущий wrapper. `@CLI_BINARY@` по умолчанию указывает на `~/.config/almaty-access/claude-native` — симлинк на этот проверенный бинарник. После auto-update проверить, куда ведёт ссылка, и повторить затронутые тесты.

## 2. Сервер, секреты и локальные файлы

Выполнить [серверный маршрут](../../server/README.md). У получателя должны быть: ограниченный `tunnel_ed25519`, его `.pub`, проверенный `known_hosts`, `proxy.auth` с правами 600. Всё лежит в собственном `~/.config/almaty-access` с правами 700; секреты не находятся рядом с раздаткой и не входят в Git.

Подготовить файлы в новой папке; сверить их содержимое без показа proxy.auth. Сначала проверить syntax:

```sh
sh -n /путь/к/подготовленному/claude-almaty
sh -n /путь/к/подготовленному/chrome-almaty.command
plutil -lint /путь/к/подготовленному/local.almaty-access.tunnel.plist
```

Пути здесь заменяет Codex на реальные с корректными кавычками. Проверить: единственный `-L` привязан к `127.0.0.1`; отдельные `known_hosts` и key; `StrictHostKeyChecking=yes`, `BatchMode=yes`, `ExitOnForwardFailure=yes`; в plist нет пароля. Пользователь подтверждает конкретный план установки. Установить wrapper/Chrome launcher 700, профиль 600, plist 600, не перезаписывая чужой существующий файл. Папка `~/.local/bin` должна быть в PATH либо команды запускаются абсолютным путём.

## 3. Туннель и первичная проверка

Перед автозапуском проверить SSH в переднем плане **без Claude** по аргументам подготовленного plist. Полученная команда не содержит пароль proxy. Она должна удерживать соединение и не открывать shell. Завершить `Ctrl+C`, затем загрузить только собственную службу:

```sh
launchctl bootstrap "gui/$(id -u)" "$HOME/Library/LaunchAgents/local.almaty-access.tunnel.plist"
launchctl print "gui/$(id -u)/local.almaty-access.tunnel"
lsof -nP -iTCP:48921 -sTCP:LISTEN
```

Listener должен принадлежать именно PID SSH этой службы, с ожидаемыми `-i`, host key и адресом VPS. Один открытый порт не удостоверяет туннель: чужой локальный proxy может тоже слушать 48921. Ошибку занятого порта не исправлять заменой `127.0.0.1` на `0.0.0.0`.

Сначала проверить требование proxy auth без учётной записи сервиса; затем authenticated IP запрос через диагностический инструмент, читающий файл сам. Пароль не передавать в аргументах `curl`. В журнал записать только статус, внешний IP, версии и время. Сам пароль браузера при необходимости владелец вводит в системный proxy-auth dialog, не в адресную строку.

## 4. Проверка ограничения CLI до входа

Профиль сначала испытывается на безвредных диагностических дочерних процессах под `sandbox-exec`, не на аккаунте. Например, следующая команда проверяет чтение профиля и локальную работу:

```sh
/usr/bin/sandbox-exec -f "$HOME/.config/almaty-access/proxy-only.sb" /usr/bin/true
```

Далее одна матрица проверяется из того же профиля: прямые TCP IPv4/IPv6 к **работающим контролируемым** endpoint, UDP, DNS через системный resolver и TCP/UDP53, свежий HTTPS через proxy, `NO_PROXY=*` и полностью удалённые proxy vars, child shell/Python/Node/git, hooks и MCP. Нужны внешнее наблюдение трафика и реальные отрицательные запросы: отсутствие DNS-ответа не доказывает отсутствие отправки пакета. Проверки с URL и IP-литералами раздельные.

Профиль разрешает локальные файловые и многие IPC-операции по `(allow default)`. Он не заявляет защиту от произвольного host-exec helper через AppleScript, сторонний Unix socket/desktop service или сознательного изменения файлов владельцем. Перед принятием проверить установленные MCP/hooks, локальные relay, `osascript`, LaunchServices и другие пути запуска на хосте. `/usr/bin/open` запрещён отдельно, но это не исчерпывающий запрет всех внешних исполнителей. Защита относится к проверенному дереву CLI, а не ко всему компьютеру.

Для согласованного теста обрыва отключить **только** этот LaunchAgent:

```sh
launchctl bootout "gui/$(id -u)/local.almaty-access.tunnel"
```

Проверить новые и уже выполняющиеся запросы; прямой выход должен остаться запрещён. Затем повторный `bootstrap` с тем же plist. Обычное убийство SSH не подходит для устойчивого теста: `KeepAlive` перезапустит его. Отдельно проверить неверный пароль, остановку собственного тестового gost, Wi-Fi, sleep/wake и reboot. Обрыв делается только в согласованное окно; чужие службы не останавливать.

После этих тестов запуск `claude-almaty --version` подтверждает CLI без авторизации. Передавать `--dangerously-skip-permissions` или выключать TLS для прохождения теста нельзя. Идущий дальше процесс наследует профиль даже если удалит proxy-переменные; это и требуется проверить.

## 5. Отдельный Google Chrome и iTerm2

Установи [iTerm2](https://iterm2.com/) и [Google Chrome](https://www.google.com/chrome/)
штатным способом, если их нет. Не переустанавливай существующие рабочие программы.
Codex проверяет реальные пути приложений и адаптирует шаблон, если Chrome лежит
в пользовательском Applications. Сохраняй корректное shell quoting путей.

Перед входом запусти из iTerm2:

```sh
"$HOME/.local/bin/chrome-almaty.command" --check
```

Создаётся собственный `~/.config/almaty-access/chrome`, без старых cookies.
Браузер получает один HTTP proxy, resolver rules, отключение QUIC и
непроксируемого WebRTC UDP. Пароль proxy при запросе вводится владельцем в
браузерный диалог из своего локального файла, не в чат и не URL. Codex может
подготовить копирование значения в локальный буфер с согласия, без stdout/logs;
после вставки очистить буфер. Не показывай файл на записи экрана.

Проверь IP своего VPS. Перед контрольными опытами закрой только этот Chrome,
сверь в chrome://version его Profile Path и командную строку; новый запуск должен
использовать этот user-data-dir и единственный proxy. Не считать обычный профиль
в меню Chrome эквивалентным. На повторном запуске Chrome может передать URL уже
работающему процессу: после изменения флагов закрыть процесс этого профиля целиком.

При остановке своего gost и отдельно службы SSH новая HTTPS-страница с новым
параметром должна перестать загружаться; после восстановления — снова показывать
IP VPS. Не добавлять DIRECT и не возвращать proxy-bypass исключения. Обнаруженный
прямой выход исправить и повторить опыт. Без внешнего firewall не обещать запрет
любого возможного вспомогательного процесса: записать эту область в протокол.
Детали [Chromium proxy](https://chromium.googlesource.com/chromium/src/+/HEAD/net/docs/proxy.md).

После приёмки открой рабочую страницу в том же профиле:

```sh
"$HOME/.local/bin/chrome-almaty.command" --claude
```

Пройди оба результата из [этапа 9](../../SETUP.md): ответ веб-чата, затем вход
Claude Code в iTerm2 и локальная задача. Для CLI используй manual login flow:
ссылку скопировать из терминала и открыть в этом Chrome, показанный код вернуть
в терминал. Если flow завис на localhost, выясни текущий документированный способ
ручного входа; не отключай proxy и не открывай обычный браузер.

Создай пользователю профиль iTerm2 или маленькие .command ярлыки с точными
командами его установки. Ярлык CLI выполняет `cd` в выбранную папку и запускает
`claude-almaty`, ярлык браузера вызывает `chrome-almaty.command --claude`.
Существующие профили iTerm2 сохраняются. Проверь запуск из нового окна iTerm2.

## Панель, ежедневный запуск и обновление

Agentbelt — необязательная панель **только macOS/iTerm2**. Это не proxy и не доказательство изоляции. Установку и собственный LaunchAgent выполнять по [upstream README](https://github.com/vakovalskii/agentbelt) после чтения MIT LICENSE; исходник не вложен в комплект. Кнопки должны запускать `claude-almaty`, не исходный `claude`. Исторические исключения для iTerm2 IPC/локального порта не переносить автоматически: они расширяют поверхность обхода и требуют собственного теста.

После проверок на этом компьютере ежедневный порядок: проверить службу → проверить свежий внешний IP/доступность → открыть защищённый браузер → `claude-almaty` в своей папке проекта. Красный статус — причина проверить слой, а не переключать direct. Статусы «туннель», «proxy», «API», «изоляция» раздельны; HTTP401 не означает бан.

CLI/Chrome могут обновляться автоматически. Записать новую версию, не считать старый протокол действующим; повторить минимум direct tests, отключение туннеля и браузерный вход. Не заменять native CLI wrapper-скриптом и не создавать рекурсивный `claude-native → claude-almaty`.

## Откат без удаления проектов

1. Закрыть только сеансы комплекта; `launchctl bootout` только `local.almaty-access.tunnel`.
2. По описи переместить из установленных мест именно plist и launcher этого комплекта в выбранную папку отключённых файлов. Если существовал прежний файл, восстановить его из согласованного точечного перемещения; не переписывать остальные LaunchAgents.
3. `proxy.auth`, ключ и отдельный Chrome profile сначала оставить с правами 600/700. Их удаление — отдельное подтверждение владельца. Серверный ключ отозвать в соответствующем authorized_keys; административный ключ не трогать.
4. Проверить обычную работу Mac и сохранность проектов. Системный proxy, firewall и обычный Chrome комплект не менял: сбрасывать их не требуется. Никаких `rm -rf ~/.claude`, глобального Keychain reset или отключения всех LaunchAgents.

Синтаксическая проверка выдачи не подтверждает установку на этом Mac. Агент выполняет здесь сетевые проверки, web-chat, CLI-задачу и повторный запуск обоих; сохраняет фактические результаты и исправления.

Background service, `claude agents`, `--bg` и `/background` этим маршрутом не поддерживаются: supervisor может запустить бинарник напрямую, а старый профиль не закрывает все host IPC. Использовать только foreground local CLI.
